# README recording (VHS)

The README's [`docs/demo.gif`](../docs/demo.gif) links directly to the
[`docs/demo.mp4`](../docs/demo.mp4) video. Both are generated by
[Charmbracelet VHS](https://github.com/charmbracelet/vhs). Styling follows the
Discuss CLI's terminal scenes: Catppuccin Mocha and a 1280px-wide terminal.

## Re-record

Prerequisites:

- A current native `openjev` on PATH with `serve`, `demo`, and the demo's `request`
  field (not v0.1.0).
- Qwen3-0.6B already cached: `openjev models pull qwen3-0.6b` (one-time).
- VHS, ttyd, FFmpeg, Python 3, and a browser supported by VHS. On macOS:
  `brew install vhs ttyd ffmpeg`; Menlo is the recording font.

From the repository root:

```sh
# Use the freshly built Metal binary, or omit PATH= to use your installed build
PATH="$PWD/target-m2-metal/release:$PATH" bash demo/record.sh
```

The tape runs `demo/session.py`, which types the exact commands it executes:

```sh
openjev serve --offline --model qwen3-0.6b --device metal --port 18787
openjev demo --base-url http://127.0.0.1:18787 --quiet
```

The first scene shows **real model startup**: launching the server, waiting for
`/readyz`, its JSON response, and the observed startup duration. Native logs are
saved, rather than flooding the terminal. Once ready, the same server remains
resident while a separate demo client process makes all eight HTTP requests.

For each example, `present.py` displays the exact request's state, instructions,
and labelled options/Score levels, followed by a separate result screen:

- Single-question examples: **8 seconds of inputs**, then **6 seconds of results**.
- Mixed Choice/Noul/Score example: **14 seconds of inputs**, then **10 seconds of results**.

Result screens show a compact projection: example, model, typed answer values,
and rounded HTTP milliseconds. Full requests/responses—including probabilities,
confidence, legends, usage, and metadata—are retained in
`out/demo-recording/responses.jsonl`. The serial fallback also appears onscreen.
This presentation is not a new CLI output schema; `openjev demo --pretty` emits
the normal full rows.

## Runtime and cleanup

The wrapper refuses an occupied port; set `DEMO_PORT=18788` for another port.
The session owns and stops only its child processes, including on interruption.
It never attaches to or shuts down a pre-existing server. It uses `--offline`
and Metal on Apple Silicon macOS (CPU elsewhere). Startup has a 120-second
readiness limit; the tape's total capture window is sized for this Mac. A slower
machine may need a longer `Sleep` before the final `Wait` in `readme.tape`.

## What the recording proves (and does not)

- Real startup and eight live HTTP requests; no mocked or substituted predictions.
- Input cards come from the actual request sent by the demo, not a separately
  maintained copy of the examples. Responses are received before the paced
  input/result presentation; card pauses do **not** represent inference delays.
- Playback is **not** a speed benchmark. `http_ms` is the real client's round-trip
  measurement, not the time a result card stays onscreen.
- The model can be wrong. Probabilities are conditional and uncalibrated; Score
  is the expected zero-based level index. No result is replaced to look better.
- The mixed request shows the current shared-to-serial fallback.

The capture uses Qwen3-0.6B Q8_0 on an Apple M3 Pro with Metal. Raw logs,
unmodified request/response rows, a completion marker, and a final-frame PNG
stay in ignored `out/demo-recording/`. Review those and sampled video frames
before committing a new recording. These features are not in v0.1.0.

Quick checks:

```sh
shellcheck demo/record.sh
python3 -m py_compile demo/present.py demo/session.py
python3 -m unittest discover -s demo -p 'test_*.py'
vhs validate demo/readme.tape
ffprobe -v error -show_entries format=duration,size -of json docs/demo.mp4
```
