INCIDENT OVERVIEW
At 09:12 UTC on 14 March, the Atlas gateway in the west region crossed its error-rate alert threshold. Triage assigned SEV-2 because a subset of write requests failed while reads continued normally. The central and east regions remained within their normal error budgets. Edge operations acknowledged the page first at 09:15. Storage operations joined at 09:23, and messaging operations monitored downstream effects without taking ownership. No evidence indicated customer data loss. The status page was updated every fifteen minutes until recovery was confirmed.

CHANGE HISTORY
A routing policy update had been applied at 08:47, before the incident window. The update selected a newly introduced metadata field when choosing an upstream pool. The production Catalog service still returned stale metadata using the prior field shape for one west-region shard. Staging had fresh metadata and therefore did not reproduce the fault. Development used a static fixture and was also unaffected. No database migration or frontend release occurred in the relevant interval. Certificate monitors remained green, and process memory stayed below sixty percent on every gateway host.

DETECTION AND TRIAGE
The first alert came from the write error-rate threshold, not latency or capacity. Synthetic checks then reproduced failures for create and update operations routed through the affected pool. Read-only checks succeeded. Request traces showed the gateway rejecting a field before any durable write was attempted, supporting the conclusion that data was not lost. The Catalog dependency returned stale metadata, while Identity and Ledger responses matched their contracts. Engineers compared current and previous routing configurations and isolated a schema mismatch as the primary technical cause.

MITIGATION
At 09:34 the team rolled back the routing policy. The rollback reduced the failure rate but did not clear cached route selections already held by gateway workers. At 09:41 operators rerouted west-region traffic through the central pool, which reduced new failures to baseline. They did not add capacity because CPU, memory, queue occupancy, and connection counts were healthy. A controlled cache refresh followed. Write requests remained degraded briefly while retries and queued operations drained; reads and notifications stayed available. Rollback alone was therefore not sufficient, although it was a useful first mitigation.

RECOVERY
Synthetic checks were the primary signal used to confirm recovery. The success-rate graph recovered first, latency recovered second, and backlog drain lagged behind both. Queue depth was observed as supporting evidence but was not the final confirmation signal. Support ticket volume was too sparse to establish recovery. At 10:18 all synthetic create, update, and read scenarios had passed for twenty consecutive minutes. The status page moved to monitoring. At 10:42, after one more clean observation interval, the incident was closed as resolved after monitored recovery rather than cancelled or left open.

CONTROL HANDLING
The on-call did not bypass the normal receipt gate. Proposed routing changes were rendered, reviewed by a second operator, and applied through the approved control path. An emergency bypass was discussed but rejected because rerouting could be completed within the normal path. Audit records contain the reviewer identity and configuration digest. This benchmark asks only whether a bypass occurred; the answer supported by the record is no. The record does not claim that every unrelated operational control was reviewed.

CUSTOMER AND COMMUNICATION IMPACT
Some west-region customers saw failed write attempts and successful retries. Read requests remained available. Notifications were delivered normally. The team found no evidence of committed records disappearing or of requests being acknowledged before rejection. Communications used a fifteen-minute cadence. Each update distinguished observed facts from hypotheses: the first noted elevated write failures, the second noted the routing rollback, the third noted rerouting and improving success, and the final update noted monitored recovery.

ROOT CAUSE
The direct cause was a schema mismatch between a routing policy expecting a new Catalog metadata field and one production shard returning the prior shape. The introducing change was the routing policy update applied before the incident. Stale Catalog metadata made the mismatch region-specific. A missing pre-apply compatibility check allowed the configuration to pass validation. Certificate expiry and memory exhaustion were ruled out by direct measurements. The database, Identity service, Ledger service, frontend, and notification pipeline were not causal.

FOLLOW-UP ACTIONS
The highest-priority action is to add configuration validation that checks routing policies against every active Catalog schema version before publication. The Atlas gateway team owns that action and must also review the runbook. A dashboard redesign is planned but is secondary. Training will be scheduled after the validation rule and runbook revisions are complete. Security and finance teams receive the final review record but do not own the operational runbook. The Catalog team will add freshness telemetry and a forced-refresh procedure for shard metadata.
